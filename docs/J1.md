# Journal - Jour 1

## Questions à résoudre

### Qui produit la mesure, qui la transporte, qui la conserve et qui l'affiche ?

- **Produit** : un device du kit démo (capteur température/CO2), qui publie
  sur le broker MQTT de démonstration un message de télémétrie sur
  `campus/v1/devices/{deviceId}/telemetry` — contrat observé et documenté
  dans [ADR 0004](decisions/0004-contrat-mqtt-placeholder.md).
- **Transporte** : le broker MQTT (le broker de démo distant en ce moment,
  Mosquitto localement via `docker-compose.yml`), puis le client mqtt.js du
  backend ([driving/mqtt/client.ts](../backend/src/driving/mqtt/client.ts))
  qui reçoit le message brut.
- **Conserve** : l'adapter
  [driving/mqtt/handlers.ts](../backend/src/driving/mqtt/handlers.ts) valide
  le payload (Zod, `schemas.ts`) et appelle
  `MeasurementIngestionService.ingest()`, qui écrit en PostgreSQL via
  `PrismaMeasurementRepository` (dédup/retard appliqués au passage — voir
  `domain/services/dedup.ts`).
- **Affiche** : l'app mobile
  ([RoomDetailScreen.tsx](../mobile/src/screens/RoomDetailScreen.tsx))
  interroge `GET /rooms/:id/measurements/latest`
  ([driving/api/routes/rooms.ts](../backend/src/driving/api/routes/rooms.ts))
  via `fetchLatestMeasurements` (`mobile/src/api/client.ts`) et affiche
  valeur, unité et date de chaque métrique de la salle.

### Pourquoi une API et un broker ont-ils des rôles différents ?

Le broker MQTT est fait pour la diffusion continue, asynchrone et
faible coût côté device : les capteurs publient dès qu'ils ont une mesure,
sans savoir qui écoute ni maintenir de connexion HTTP. L'API REST, elle,
sert la consultation à la demande (requête/réponse) : le mobile veut
« l'état actuel de cette salle » à l'instant où l'utilisateur ouvre l'écran
ou tire pour rafraîchir, pas un flux continu qu'il devrait parser et
bufferiser lui-même.

Le backend est le pont entre les deux rythmes : il consomme MQTT en continu
(`driving/mqtt`), écrit l'état en base via le domaine, et expose un
instantané cohérent en HTTP (`driving/api`). Les deux adapters appellent le
même domaine (`MeasurementIngestionService`, dédup, fraîcheur, alertes) sans
jamais s'appeler l'un l'autre — voir
[ADR 0001](decisions/0001-architecture-hexagonale.md) — donc la règle
« quelle mesure fait foi » n'existe qu'à un seul endroit, qu'elle soit
consultée juste après réception MQTT ou une heure plus tard via l'API.

### Qu'affiche le téléphone pendant le chargement ou si aucune mesure n'existe ?

Dans `RoomDetailScreen.tsx` :

- **Chargement** : un `ActivityIndicator` centré (état `loading`).
- **Erreur API** (serveur injoignable, session expirée, etc.) : un message
  d'erreur et un bouton « Réessayer » qui relance l'appel.
- **Aucune mesure** (liste vide renvoyée par l'API, salle sans device ou
  sans mesure reçue) : le message « Aucune mesure reçue pour l'instant pour
  cette salle. ».

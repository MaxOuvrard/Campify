# Journal - Jour 3

## Objectifs du jour

Sécuriser et fiabiliser le système IoT : identité des devices, validation
des messages entrants, dédup/ordre, fraîcheur et capteur silencieux,
résilience broker/backend, secrets hors du dépôt, logs centralisés et
corrélables, ADR sur les décisions structurantes.

## Questions à résoudre

### Comment distinguer sans ambiguïté plusieurs capteurs simulés qui publient en parallèle ?

Le `deviceId` est résolu **depuis le topic MQTT**
(`campus/v1/devices/{deviceId}/telemetry`), jamais depuis le payload —
voir [ADR 0004](decisions/0004-contrat-mqtt-placeholder.md). Ce choix
n'a de sens que si le topic fait foi, donc que seul le vrai device peut y
publier : le broker local impose désormais une identité MQTT par device
(mot de passe + ACL restreignant chaque identité à sa propre télémétrie)
— voir [ADR 0008](decisions/0008-identite-devices-authentification-mqtt.md).
Chaque device a en plus un `boot_id` stable par démarrage (préfixe du
`message_id`), qui permet de suivre sa continuité dans le temps
indépendamment du contenu des mesures. Preuve : scénario "Isolation des
devices" et "Usurpation d'un device" dans le tableau de recette
ci-dessous.

### Quelles données entrantes doivent être refusées avant d'atteindre le cœur du système ?

Trois niveaux, dans l'ordre, tous avant la base vérifiée :

1. **Structure** (`driving/mqtt/schemas.ts`, Zod) : JSON invalide, champ
   obligatoire absent ou mal typé — rejeté avant même d'appeler le
   domaine.
2. **Plausibilité physique** (`domain/services/plausibility.ts`) : valeur
   non finie (NaN/Infinity) ou hors bornes configurées pour son type
   (ex. température) — nouveau ce jour, voir scénario "Payload invalide".
3. **Dédup/ordre** (`domain/services/dedup.ts`, ADR 0005, déjà en place
   depuis J2) : doublon exact ou mesure en retard.

Dans tous les cas, la mesure est quand même tracée en base brute
(TimescaleDB, sans filtre) — seule la base vérifiée (ce qui alimente
l'API) est protégée.

### Comment détecter qu'un capteur ne fournit plus une information suffisamment fraîche ?

`domain/services/freshness.ts` (`isFresh`), déjà en place depuis J2 :
`fresh` par mesure est dérivé du timestamp **du payload**
(`observed_at`), jamais de la date de réception — indispensable pour ne
pas confondre "reçu à l'instant" et "réellement récent" (voir scénario
"Message retained"). Seuil configurable (`DEVICE_STALE_THRESHOLD_MS`, 5
min par défaut). Preuve du délai exact : scénario "Capteur silencieux".

### Comment le système se comporte-t-il lorsqu'un message est dupliqué, retardé ou invalide ?

- **Dupliqué** (même `message_id`) : rejeté, l'état courant ne change
  pas, tracé en base brute quand même.
- **Retardé** (timestamp antérieur au dernier connu) : rejeté pour la
  même raison — ne remplace jamais un état plus récent.
- **Invalide** : rejeté au niveau structure ou plausibilité (ci-dessus),
  jamais de crash, toujours loggué avec un motif explicite.

Voir scénarios "Doublon", "Désordre et replay", "Payload invalide".

### Que se passe-t-il si le broker MQTT devient indisponible puis revient ?

`mqtt.js` reconnecte automatiquement ; on journalise désormais chaque
transition (`eventType: mqtt_connection`, voir
[docs/architecture.md, section "Connexion MQTT"](architecture.md)). La
reprise est automatique côté broker↔backend et broker↔devices. Voir
scénario "Broker indisponible".

### Quels secrets et paramètres de configuration ne doivent jamais être versionnés dans Git ?

Identifiants de bases de données, `JWT_SECRET`, identifiants MQTT (locaux
ou du kit). Audit fait ce jour : **un vrai secret était committé** —
l'adresse et le mot de passe du broker de démonstration du kit, en clair
dans [ADR 0004](decisions/0004-contrat-mqtt-placeholder.md) depuis le
commit `6b50ec1` (J1). Retiré des fichiers actuels ; reste présent dans
l'historique git déjà poussé sur GitHub — **décision en attente côté
équipe** : faire changer ce mot de passe (recommandé) et/ou réécrire
l'historique. Voir section Limites connues.

## Limites connues

- **Secret historique non purgé** : le credential MQTT du kit reste lisible
  dans l'historique git déjà poussé sur GitHub, malgré le retrait des
  fichiers actuels. Décision d'équipe nécessaire (rotation du mot de passe
  côté kit recommandée ; réécriture d'historique volontairement non faite
  unilatéralement — action destructive).
- **Broker du kit (VPS)** hors de notre contrôle : l'ACL/auth par device
  posée cette session ne protège que le broker local. On ignore si le kit
  authentifie ses devices individuellement.
- **File d'attente du broker non bornée testée** : la session persistante
  (ADR 0010) élimine la perte observée sur une coupure de l'ordre de la
  minute ; le comportement sur une coupure très longue avec un volume
  élevé (limites par défaut de Mosquitto) n'a pas été testé.
- **Montée en charge** : testée jusqu'à ~500 msg/s en agrégé sur 3 devices
  simulés localement, pas au-delà, et pas avec une charge API HTTP
  concurrente (lecture mobile pendant la charge MQTT).
- **QoS sur le broker du kit** : le comportement réel de retenue/replay du
  broker partagé n'a pas été vérifié (tests faits uniquement sur le broker
  local, que nous contrôlons entièrement).
